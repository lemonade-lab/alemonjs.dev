# 版本兼容矩阵

版本兼容分为“工作台运行时”“机器人项目运行时”“系统插件协议”三层。升级其中一层前，先确认另外两层没有被隐式改变。

| 组件     | 当前依据                     | 兼容要求与建议                                                              |
| -------- | ---------------------------- | --------------------------------------------------------------------------- |
| ALemonX  | `v0.2.30`                    | 使用同一工作区运行；升级前备份 `workspace/` 与运维数据。                    |
| Node.js  | 环境检查建议 `22.22.3+`      | 机器人依赖的 `engines` 优先；Node.js 25 等非 LTS 版本可能被依赖拒绝。       |
| ALemonJS | 由机器人 `package.json` 锁定 | 以项目 lockfile 和框架版本说明为准，不由 ALemonX 自动替换。                 |
| MCP      | MCP 2025-06-18 或兼容实现    | 客户端必须支持工具 schema、结构化结果和真实用户确认。                       |
| 系统插件 | `alx/v1` runner 协议         | `alx.json`、平台资产和运行时必须匹配当前宿主；插件数据保存在 `store/<id>`。 |
| Docker   | 镜像与工作区分离             | 重建镜像前持久化挂载 `/app/workspace` 和数据目录。                          |

## 升级前后检查

```text
记录 alx --version 与项目 lockfile
→ 备份 workspace、store 和 ops.db
→ 检查环境与插件兼容性
→ 先在单个项目运行 install/build/verify
→ 再升级生产工作台并观察日志
```

系统插件升级不会删除 `workspace/store/<插件 ID>`；同 ID 的工作区插件优先于程序内置或旧兼容目录。旧手动插件应先迁移到工作区管理目录，再切换到正式 Release。

## 兼容性判断原则

- 读取类 API 的新增字段通常向后兼容，集成方应忽略未知字段。
- `confirm`、任务状态和 MCP 工具名属于安全边界，不应依赖旧客户端的隐式批准行为。
- 运行时或平台资产不匹配时应显示“不兼容”，不要静默降级为任意平台执行。
- 发布后变更 `id` 会被视为新插件；需要迁移时保留旧目录和数据。
